01 · The big picture

You built a single-page application (SPA). That means the browser downloads one HTML file and one JavaScript bundle, and from then on JavaScript swaps the content on screen. Clicking "Hotels" never asks the server for a new page — React just renders different components.

The app has two sides:

Guest sideanyone visiting
↓

↓

↓
Room Detailspick dates → check availability → book

↓
Register Hotelmodal form → becomes owner
↓
Dashboardtotal bookings + revenue
↓
Add Roomimages, price, amenities
↓

Two experiences, one React app. Both read and write the same shared state.

The single most important idea: the room a guest books and the room an owner adds are the same array in memory. Add a room in the owner dashboard, then open /rooms — it's there. That's shared state, and it's what Context gives you.

The boot chain. Everything you see is under #root.

Why index.html is nearly empty

  <div id="root"></div>
  <script type="module" src="/src/main.jsx"></script>
</body>

That empty div is the mount point. React takes ownership of it and builds the entire UI inside. If JavaScript fails to load, the user sees a blank page — that's the trade-off of an SPA.

The provider sandwich in main.jsx

<BrowserRouter>

gives everything below it access to the URL + navigation

<ClerkProvider>

gives everything below it rooms, bookings, hotel, toasts

…and every page and component you wrote

A real bug you'd hit if you reordered these: put <AppProvider> outside <BrowserRouter> and the app crashes, because useNavigate() has no router to talk to. Provider nesting is not decoration — it's a dependency graph.

05 · JSX — HTML-shaped JavaScript

JSX is not HTML and it's not a template language. It is syntax sugar for function calls. Vite compiles this:

<p className="text-gray-500">{room.hotel.city}</p>

into roughly this:

jsx('p', { className: 'text-gray-500', children: room.hotel.city })

That's why the rules are what they are:

RuleReasonIn your code
className not classclass is a reserved JS keywordeverywhere
htmlFor not forsame reasonHero.jsx labels
One root element per returna function returns one valueevery component
{ } escapes into JSanything inside is an expression{currency}{room.pricePerNight}
Tags must self-close<img />, <input />HotelCard.jsx
Component names start uppercaselowercase = a DOM tag, uppercase = your component<StarRating /> vs <div>

Inside { } you can put an expression, never a statement. That's why you see ternaries and && instead of if:

// works — a ternary is an expression
{booking.isPaid ? "Paid" : "Unpaid"}

// does NOT work — if is a statement
{if (booking.isPaid) ...}

Template literals let you build class strings conditionally — this pattern is all over your Navbar:

className={`fixed top-0 w-full ${isScrolled ? "bg-white/80 shadow-md" : "py-4"}`}

06 · Components & props

A component is a function that takes props and returns JSX. That's the whole definition. Props are the function's parameters — data flowing down from parent to child.

Your Title.jsx is the cleanest example in the project:

const Title = ({ title, subTitle, align, font }) => (
  <div className={`flex flex-col items-center text-center
    ${align === "left" && "md:items-start md:text-left"}`}>

    <p className="text-sm text-gray-500/90 mt-2">{subTitle}</p>
  </div>
);

Written once, used five ways across the app:

07 · State — useState

Props come from outside; state is owned by the component. State is memory that survives re-renders, and changing it tells React to re-render.

const [destination, setDestination] = useState("");
//     ↑ current value  ↑ the only way to change it   ↑ initial value

Your Hero.jsx holds four pieces of state, one per form field:

const [destination, setDestination] = useState("");
const [checkIn,     setCheckIn]     = useState("");
const [checkOut,    setCheckOut]    = useState("");
const [guests,      setGuests]      = useState(1);

The state loop. Every interaction in your app is a lap around this circle.

Three things about useState that trip everyone up

1. Setting state does not change the variable immediately.

setGuests(3);
console.log(guests); // still the OLD value — this render's `guests` is a const

The new value shows up on the next render. Think of a re-render as calling your component function again with fresh values.

2. Use the updater function when the new value depends on the old one. You did this correctly everywhere in AppProvider.jsx:

setRooms((prev) => [room, ...prev]);          // ✅ safe
setRooms([room, ...rooms]);                   // ⚠️ can use a stale `rooms`

3. Lazy initial state — your Navbar uses the function form so window.scrollY is only read once, not on every render:

const [atTop, setAtTop] = useState(() => window.scrollY <= 10);

Object state: the AddRoom pattern

Instead of five separate useState calls, AddRoom.jsx groups related fields into one object — and note how updates must copy then override:

const [inputs, setInputs] = useState({
  roomType: "",
  pricePerNight: "",
  amenities: { "Free WiFi": false, "Free Breakfast": false, /* … */ },
});

// toggling one nested amenity — spread at EVERY level you change
setInputs((prev) => ({
  ...prev,
  amenities: { ...prev.amenities, [amenity]: !prev.amenities[amenity] },
}));

Miss the inner ...prev.amenities and you wipe out the other four checkboxes. Miss the outer ...prev and you lose roomType and price.

08 · Events & controlled forms

React events look like DOM events but are synthetic — React wraps them for cross-browser consistency. You attach them as props, camelCased: onClick, onChange, onSubmit, onKeyDown.

Controlled inputs

An input is "controlled" when React state is the single source of truth:

<input
  value={destination}                              // state → input
  onChange={(e) => setDestination(e.target.value)}  // input → state
/>
statedestination = "Du"
→
<input value>shows "Du"
→
user types "b"onChange(e)
↻
setDestination("Dub")

A closed loop. The DOM never holds truth the state doesn't know about.

Form submission

Every form in your app calls event.preventDefault() first. Without it, the browser does a full page reload and your SPA restarts:

const handleSearch = (event) => {
  event.preventDefault();          // ← stop the browser's default submit
  rememberCity(destination.trim());
  const params = new URLSearchParams();
  if (destination.trim()) params.set("destination", destination.trim());
  navigate(`/rooms?${params.toString()}`);
};

Smart form details you got right

  • Linked date inputs — picking a check-in date later than check-out clears the check-out (Hero.jsx:84, RoomDetails.jsx:149).
  • Dynamic min — min={checkInDate || today()} makes invalid ranges unpickable in the calendar itself.
  • Disabled until valid — the check-out input is disabled={!checkInDate}.
  • Event bubbling stopped — in HotelReg.jsx the overlay has onClick={close} but the form has onClick={(e) => e.stopPropagation()}, so clicking inside the dialog doesn't close it. That's a classic modal pattern.

10 · Rendering lists & the key prop

You render arrays with .map(), which turns each data item into an element:

{filteredRooms.map((room) => (
  <div key={room._id}>
    <img src={room.images[0]} alt={`${room.hotel.name} room`} />
    <p>{room.hotel.name}</p>
  </div>
))}

Why key is not optional

key is React's identity tag for a list item. Without it React can only match items by position, and position lies the moment you insert, delete, or reorder.

key = index❌ breaks on insert
Before: [0:A, 1:B]
↓ prepend C
After: [0:C, 1:A, 2:B]

React thinks item 0 just changed text from A to C, and reuses A's DOM node — carrying over scroll position, input values, focus.

key = room._id✅ stable identity
Before: [a1:A, b2:B]
↓ prepend C
After: [c3:C, a1:A, b2:B]

React sees c3 is new and a1/b2 just moved. It inserts one node and leaves the others completely alone.

This matters concretely in your app: addRoom prepends with [room, ...prev], and bookRoom does too.

This is exactly why booking.js exists:

let idCounter = 0;
export const createId = (prefix) =>
  `${prefix}_${Date.now().toString(36)}${idCounter++}`;

The timestamp alone isn't enough — two rooms added in the same millisecond would collide. The counter guarantees uniqueness. In a real app the database would hand you these ids.

Index as key is acceptable when the list never reorders, never filters, and items have no state — which is why key={index} in StarRating.jsx (always five fixed stars) is fine.

11 · Immutability — the rule behind every state update

React decides whether to re-render by comparing the reference of old state to new state. Mutate an array in place and the reference is identical — React sees no change and your UI silently doesn't update.

// ❌ mutation — same array reference, React ignores it
rooms.push(newRoom);
setRooms(rooms);

// ✅ new array every time
setRooms((prev) => [newRoom, ...prev]);

The four operations, as you wrote them

OperationYour codeWhere
AddsetRooms((prev) => [room, ...prev])addRoom
Update oneprev.map(r => r._id === id ? {...r, isAvailable: !r.isAvailable} : r)toggleRoomAvailability
Removeprev.filter(b => b._id !== bookingId)cancelBooking
Update nested{...prev, amenities: {...prev.amenities, [k]: v}}AddRoom

Memorise these four. map to update, filter to delete, spread to add, spread-at-every-level for nesting. Every React state update you ever write is one of these. Note they're all non-mutating array methods — push, splice, sort, and reverse all mutate, which is why AllRooms.jsx writes [...sorted].sort(...) and not sorted.sort(...).

12 · useEffect & cleanup

Rendering must be pure: given the same props and state, produce the same JSX and touch nothing else. But real apps need to touch the outside world — scroll listeners, timers, the document body. useEffect is the escape hatch that runs after React has painted.

useEffect(() => {
  /* the effect */
  return () => { /* the cleanup */ };
}, [deps]);

Every effect in your project, and why it needs cleanup

1. Scroll to top on navigation — App.jsx:23

useEffect(() => {
  window.scrollTo(0, 0);
}, [pathname]);

Without this, navigating from the bottom of the room list to a detail page dumps you halfway down the new page. A router quirk every SPA has to fix. No cleanup needed — nothing was subscribed.

2. Scroll listener — Navbar.jsx:48

useEffect(() => {
  const handleScroll = () => setAtTop(window.scrollY <= 10);
  window.addEventListener("scroll", handleScroll, { passive: true });
  return () => window.removeEventListener("scroll", handleScroll);
}, []);

The cleanup is mandatory. Without it, every remount adds another listener that never goes away — a memory leak that gets slower over time.

3. Lock body scroll while a modal or drawer is open — Navbar.jsx:55 and HotelReg.jsx:16

useEffect(() => {
  document.body.style.overflow = isMenuOpen ? "hidden" : "";
  return () => { document.body.style.overflow = ""; };
}, [isMenuOpen]);

The cleanup matters here too: if the component unmounts while the menu is open, the page would stay permanently unscrollable.

4. Auto-dismiss the toast — AppProvider.jsx:27

useEffect(() => {
  if (!toast) return;
  const timer = setTimeout(() => setToast(null), 3500);
  return () => clearTimeout(timer);
}, [toast]);

The cleanup makes this correct, not just tidy. Trigger a second toast at 3 seconds: the cleanup cancels the first timer, so the new message gets its full 3.5 seconds instead of vanishing after 0.5.

5. Escape key closes the dialog — HotelReg.jsx:17

const onKeyDown = (event) => { if (event.key === "Escape") setShowHotelReg(false); };

The most common misuse: useEffect is not for deriving data. If a value can be calculated from existing state during render, calculate it during render. 13 · useMemo — caching an expensive calculation

AllRooms.jsx filters by destination, room type, and price range, then sorts. That's four passes over the array, and it would re-run on every render — including when you just open the mobile filter drawer, which changes only openFilters.

  const matchesDestination = (room) => { /* … */ };

14 · Lifting state up

When two components need the same data, the state moves to their closest common parent. This is the problem that eventually forces you into Context.

The problem

App
↙    ↘
RoomDetailscreates a booking
MyBookingsneeds that booking

They're siblings. Neither can see the other's state.

The fix

AppProviderowns bookings + bookRoom()
↙    ↘
RoomDetailscalls bookRoom()
MyBookingsreads bookings

State moves up to a shared ancestor; both read from there.

Prop drilling is what happens if you lift state up but pass it down by hand:

App → Home → FeaturedDestination → HotelCard   // just to hand over `currency`

Two of those components don't use currency at all; they're only couriers. Multiply by a dozen values and every component signature becomes noise. That's the pain Context removes.

15 · The Context API — your app's brain

Context creates a value that any descendant can read directly, no matter how deep, without a single intermediate prop.

Without Context

↓ prop

↓

Context is a wire that skips the middle. It doesn't replace props — it replaces drilling.

The three pieces

1. Create the channel — context/AppContext.js

import { createContext } from "react";
export const AppContext = createContext(null);

2. Provide a value — context/AppProvider.jsx

const value = { currency, navigate, rooms, bookings, hotel, isOwner,
                addRoom, bookRoom, payBooking, cancelBooking, /* … */ };

return <AppContext.Provider value={value}>{children}</AppContext.Provider>;

3. Consume it — context/useAppContext.js

export const useAppContext = () => {
  const context = useContext(AppContext);
  if (!context) throw new Error("useAppContext must be used inside <AppProvider>");
  return context;
};

That guard clause is excellent practice. Forget the provider and you get a clear error naming the exact problem, instead of a cryptic Cannot destructure property 'rooms' of null from somewhere deep in a component.

What lives in your context

KindNamesNotes
Datarooms, bookings, hotel, isOwner, showHotelReg, searchedCities, currency, user, currentUserThe nouns of the app

This shape is the important lesson. Components never write to state directly — they call an action, and the action owns the rules. Look at bookRoom: it computes nights, calculates the total, stamps a status and timestamps, and generates an id. A component just says "book this room."

const bookRoom = ({ room, checkInDate, checkOutDate, guests }) => {
  const nights = nightsBetween(checkInDate, checkOutDate);
  const booking = {
    _id: createId("booking"),
    user: currentUser, room, hotel: room.hotel,
    totalPrice: room.pricePerNight * nights,
    guests: Number(guests),
    status: "pending", isPaid: false,
    /* … */
  };
  setBookings((prev) => [booking, ...prev]);
  return booking;
};

Derived state: dashboard

const dashboard = {
  totalBookings: bookings.length,
  totalRevenue: bookings.reduce((sum, b) => sum + b.totalPrice, 0),
  bookings,
};

Revenue is not stored in state. It's recalculated from bookings on every render. That's the right call: a stored total can drift out of sync with the list it summarises; a derived one physically can't.

Context's one real cost: when the provider's value changes, every consumer re-renders. Your value object is rebuilt on every AppProvider render, so any state change there re-renders every component using useAppContext. At this app's size that's invisible. At scale you'd split into multiple contexts (a rarely-changing one and a frequently-changing one) or wrap value in useMemo. Knowing the trade-off is what matters.

16 · Custom hooks

A custom hook is just a function whose name starts with use and that calls other hooks. useAppContext is yours:

// without the custom hook — repeated in ~14 files
const { rooms } = useContext(AppContext);

// with it — shorter, and it validates
const { rooms } = useAppContext();

You get three things: less import noise, a single place to add the null check, and a seam — if you ever swap Context for Redux or Zustand, you change one file and no component notices.

The Rules of Hooks

  1. Only call hooks at the top level — never inside an if, a loop, or a nested function. React tracks hooks by call order; conditional calls shuffle the order and corrupt state.
  2. Only call hooks from React functions — components or other custom hooks.

The eslint-plugin-react-hooks in your eslint.config.js enforces both, plus warns about missing effect dependencies. Take those warnings seriously — they're usually pointing at a real stale-closure bug.

Note the pattern in RoomDetails.jsx: the outer RoomDetails calls useParams() and useAppContext(), and only then can it early-return <NotFound />. The hooks run before any conditional return — that's Rule 1 in practice.

19 · The URL as state — useParams & useSearchParams

20 · Using key to reset a component

This is an advanced pattern and it's sitting at the bottom of your RoomDetails.jsx:

const RoomDetails = () => {
  const { id } = useParams();
  const { rooms } = useAppContext();
  const room = rooms.find((item) => item._id === id);
  if (!room) return <NotFound />;
  return <RoomDetailsView key={room._id} room={room} />;   // ← the trick
};

The problem it solves

You're on room A. You've picked dates, clicked "Check Availability", and selected the third photo. Now you navigate to room B. The URL changes, but React sees the same component type in the same position — so it reuses the instance and keeps all its state. You'd be looking at room B with room A's dates and availability result still on screen.

Without key
Room A → Room B
↓
same instance reused
mainImage still A's photo
dates still filled in
availability still "available"
With key={room._id}
Room A → Room B
↓
key changed → unmount + remount
fresh useState defaults
clean form, clean gallery

A changed key tells React "this is a different thing," and it throws away the old instance entirely.

The wrapper/view split exists for the same reason: the outer component reads the route and the inner one holds the state, so the inner one can be replaced wholesale. Remember this pattern — it's the standard React answer to "how do I reset a form when the id changes?"

22 · Vite, environment variables & assets

The two commands

npm run dev     # dev server, hot reload, ~instant startup
npm run build   # optimised bundle into dist/
npm run preview # serve dist/ locally to test the real build
npm run lint    # ESLint over the whole project

Vite is fast in dev because it doesn't bundle — it serves your files as native ES modules and lets the browser do the linking. Change one file and only that module reloads. For production it switches to Rollup and does bundle, minify, tree-shake, and hash filenames.

Environment variables

const PUBLISHABLE_KEY = import.meta.env.VITE_CLERK_PUBLISHABLE_KEY;

if (!PUBLISHABLE_KEY) {
  throw new Error("Missing Clerk Publishable Key. Add VITE_CLERK_PUBLISHABLE_KEY to client/.env");
}

Three rules:

  • It's import.meta.env, not process.env (that's Node/webpack).
  • Only vars prefixed VITE_ are exposed to the browser. That prefix is a safety gate — it stops you accidentally shipping a secret.
  • Anything exposed this way is public. It ends up in the JS bundle, readable by anyone. Publishable keys are designed for that; secret keys must never go here.

The fail-fast throw is good practice — a clear error at startup beats a confusing one deep inside Clerk later.

Assets: why assets.js exists

import logo from './logo.svg';
import searchIcon from './searchIcon.svg';
export const assets = { logo, searchIcon, /* …40 more */ };

Importing an image gives you the final URL after Vite hashes it (logo-BN30LNQe.svg — you can see these in client/dist/assets/). Hashing is how browsers can cache aggressively yet still pick up a changed file. Collecting them all in one module means components write assets.logo instead of managing dozens of relative import paths.

The same file exports your fake database — roomsDummyData, userBookingsDummyData, cities, facilityIcons. That facilityIcons map is a neat little pattern: it turns a string into an icon without any if-else chain.

<img src={facilityIcons[item]} alt="" />   // item === "Free WiFi" → the wifi svg

Object URLs in AddRoom — a real browser API

const selectSlot = (key, file) =>
  setImages((prev) => {
    if (prev[key]) URL.revokeObjectURL(prev[key].url);   // free the old one

createObjectURL mints a temporary blob: URL pointing at a file in memory, so you can preview an image before any upload exists. Each one holds memory until revoked — hence the revokeObjectURL when a slot is replaced. This is exactly the kind of resource management React doesn't do for you.

25 · The render lifecycle, in one picture

Everything above is really just this loop, over and over:

1. Triggera click, a keystroke, a URL change, a timer
↓
2. RenderReact calls your component functions. They must be pure — no DOM edits, no fetching.
↓
3. ReconcileReact diffs the new element tree against the old one, using key to match list items
↓
4. CommitOnly the actual differences are applied to the real DOM
↓
5. EffectsuseEffect callbacks run — cleanup first, then the new effect
↺  back to 1 on the next trigger

Why step 2 must be pure: React reserves the right to call your component more than once, to throw away a render it doesn't need, or (in Strict Mode during development) to double-invoke it deliberately to surface side effects. If rendering also mutated something, that would be unpredictable. Side effects belong in step 5.

Why step 4 is cheap: React doesn't rebuild the page. It compares two lightweight JavaScript object trees and touches only the DOM nodes that actually differ — a text node here, one attribute there. The DOM is slow; JS object comparison is fast. That's the entire performance argument for React.

A sensible order to tackle them

  1. localStorage persistence. Smallest change, most satisfying result — bookings survive a refresh. Two useEffects and a lazy useState initialiser.
  2. Protected routes. A ~15-line component; teaches you redirects and route composition.
  3. Filter bookings by user. One .filter(), but it makes you think about data ownership.
  4. Move all filters into the URL. Finishes the idea you started in AllRooms and makes every filtered view shareable.
  5. A real backend. Express + MongoDB, then swap the dummy arrays for fetch. This is where loading states, error states, and async React actually click. Because everything already goes through Context actions, you'd be changing one file — AppProvider.jsx — and no component would need to know.

That last point is the payoff of your architecture. Components ask the context for data and call context actions to change it. They never care where the data comes from. Swapping in-memory arrays for API calls touches the provider and nothing else. That's what "separation of concerns" means in practice, and you built it correctly without a server forcing you to.

27 · Check yourself

If you can answer these from memory, you understand the project. Click to reveal.

Why does <AppProvider> have to be inside <BrowserRouter>?

Because AppProvider calls useNavigate(), and that hook reads router context. A hook can only read context provided by an ancestor. Outside the router, there's nothing to read and React throws.

What actually breaks if you use key={index} on the rooms list?

addRoom prepends with [room, ...prev], so every existing item's index shifts by one. React would think item 0 changed content rather than that a new item was inserted, and would reuse the wrong DOM nodes — carrying over things like scroll position, focus, and any uncontrolled input values.

Why does the toast useEffect return clearTimeout?

Cleanup runs before the effect re-runs. If a second toast fires 3 seconds into the first one's 3.5-second timer, the cleanup cancels the stale timer so the new message gets its full duration instead of being wiped after 0.5s. It also prevents a timer firing after unmount.

Where does totalRevenue live, and why isn't it state?

It's derived: bookings.reduce((sum, b) => sum + b.totalPrice, 0), recomputed every render. Stored totals drift out of sync with the list they summarise — every add, cancel, and edit would need to remember to update it. Derived values can't drift.

What does key={room._id} on <RoomDetailsView> accomplish?

It forces a full remount when you navigate between rooms. Without it React reuses the instance, and room B would show room A's selected photo, dates, and availability result. A changed key means "different thing" — discard the old state entirely.

Why [...sorted].sort(...) instead of sorted.sort(...)?

.sort() mutates in place. sorted came from rooms.filter(), which is a new array — but the deeper habit matters: never mutate anything that could be, or could later become, state. The spread makes a copy first.

What's the difference between <Link to="/rooms"> and <a href="/rooms">?

Link intercepts the click and swaps components client-side — instant, and Context state survives. The anchor triggers a full page reload: the bundle re-downloads, React remounts from scratch, and every booking in memory is lost.

Why does useMemo in AllRooms omit openFilters from its dependencies?

Because openFilters only controls whether the mobile filter drawer is visible — it has no effect on which rooms match. Including it would recompute the whole filter-and-sort pipeline every time someone taps "SHOW". Dependencies should list exactly what the calculation reads, no more.

How does the app know to hide the Navbar and Footer on owner pages?

App.jsx reads useLocation(), computes pathname.startsWith("/owner"), and renders {!isOwnerPath && <Navbar />}. The owner section supplies its own shell through Layout.jsx and <Outlet />.

Why does createId combine a timestamp and a counter?

Date.now() has millisecond resolution, so two records created in the same millisecond would collide — and duplicate keys break React's reconciliation. The incrementing counter guarantees uniqueness within the session. A real database would issue these ids instead.

The short version

You wrote a component tree that renders from state. Local state stays local; anything two components share moved into a Context that exposes data and actions, never raw setters. The URL holds the state that should be shareable. Effects handle the few things outside React — listeners, timers, the document body — and every one of them cleans up after itself. Lists carry stable keys, updates never mutate, and a changed key is how you throw state away on purpose.

That's not a hotel booking app's worth of knowledge. That's most of React.
